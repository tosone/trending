# AGENTS.md — GitHub Trending newspaper

Notes for any agent working in this directory. Read it before you touch anything.

## What this is

A newspaper-styled page built from GitHub Trending. `index.html` is the only page: a
language dropdown and repo list on the left, repo cards on the right (title `owner/repo`,
body a Chinese summary, footer the star count and last-updated date). The data is static
JSON under `data/`, read by the page with `fetch()`.

## How to open it

Browsers do not let a `file://` page read JSON from the same directory, so double-clicking
`index.html` shows a notice. The correct way:

```bash
python3 -m http.server 8137     # http://localhost:8137/
```

On macOS, double-clicking `serve.command` is equivalent. Do **not** merge the JSON into
`.js` / bundles to dodge this, and do not fall back to CDN or `local()` fonts.
`index.html` loads the stylesheet as `assets/trending.css?v=N` — bump `N` whenever you edit
`trending.css`, otherwise a browser can keep serving the cached copy and the change looks
like it never landed.

## Layout and responsibilities

```
index.html            the only page; rendering only, no styles or data
assets/trending.css   all layout styling; do not write a second copy of the CSS in the page
assets/fonts/         self-hosted Maple Mono NF CN (fonts.css is @import-ed)
data/catalog.json     language registry (drives the dropdown; first entry is the "all" summary)
data/all.json         index of the deduped all-language board (shown by default)
data/other.json       index of repos from the overall board whose language is not covered (only in all, not in the dropdown)
data/<language>.json  index of one language's board
data/<key>.<n>.json   the actual repos: every board is cut into 300-repo chunks (all.1.json, all.2.json, …)
tools/fetch_trending.py   fetch trending + README + generate Chinese summaries
```

## Data rules

- **Every board is chunked.** `data/<key>.json` is only an index — `language`, `label`,
  `count`, `generated_at`, `first_at`, `chunk_size` and a `chunks` list — and holds no repos.
  The repos live in `data/<key>.<n>.json`, 300 per file, cut from the stars-descending list.
  `all.json` has 11 chunks, `go.json` 3, most languages 1–2. The tool reads and writes this
  layout on its own (`load_doc` / `write_doc`), so `--repos`, `--retag`, `--refresh` and a
  full run all reassemble the chunks first; `--rewrite` re-cuts existing files offline.
  The page fetches the index, paints the first chunk, then loads the rest in parallel.
- 8 languages are covered: `javascript` / `typescript` / `python` / `java` / `go` / `rust` /
  `c` / `cpp`, each in `data/<key>.json`; `data/all.json` is the deduped summary of every
  language plus `other.json`, registered as the first catalog entry, and opened by default.
- The unfiltered overall board is fetched too: repos whose language is covered are merged
  into the matching language file, the rest go to `data/other.json` and only appear in all.
  `all.json` / `other.json` are generated only by the script; never edit them by hand.
- The `PINNED` list at the top of the script holds manually pinned repos
  (openclaw/openclaw, golang/go, python/cpython, RustPython/RustPython, react/react): they
  are always collected whether or not they are trending, and are routed to their language
  file; their `windows` is empty and they carry `pinned: true`.
- Every repo must have `summary` (≤300 Chinese characters) and `pushed_at` (the footer's
  sort key).
- Every repo also carries two tag axes, both English slugs: `tags` / `primary_tag` (form:
  `app` `tool` `library` `framework` `plugin` `template` `doc` `asset` `model` `config`
  `example` `other`) and `domains` / `primary_domain` (area: `web` `mobile` `desktop`
  `devops` `ai` `data` `networking` `security` `systems` `devtools` `media` `graphics`
  `blockchain` `productivity` `learning` `embedded` `other`). Tags are produced by the tool
  exactly like summaries — new repos get them, existing ones keep them; `--retag` (optionally
  with `--repos`) recomputes them. The page filters by `domains`.
- **Data accumulates**: by default all three windows `daily` / `weekly` / `monthly` are
  fetched, deduped by repo, and merged into the list — never rebuilt or pruned. Existing
  repos only refresh live fields such as stars / update time; only new entries get a
  `summary`. The list is stored sorted by `stars` descending. Each repo carries `windows`
  (which windows it appeared in, stored but not displayed), `added_at` (first collected),
  `last_seen`, and `seen_count`.
- Do not record or display "stars gained today" (`stars_today`); sorting is 收录时间 / Star
  / last-updated only, and the page opens on 收录时间 descending.
- `data/*.json` is generated by `tools/fetch_trending.py`; do not change the structure by
  hand — change the script and run it again.
- Summaries are based on the README only; never invent version numbers, performance
  figures, or features that are not in the README. Do not mention licenses (`MIT`, `GPL`, …)
  in a summary.
- Fetching needs a logged-in `gh`; generating summaries needs `DEEPSEEK_API_KEY` (without
  it the tool falls back to an extractive summary).

## Adding a repo

You do **not** need to run the full trending update to add a repo. Use the targeted mode,
which skips all 27 trending pages and only touches the repos you name:

```bash
python3 tools/fetch_trending.py --repos owner/repo        # add or refresh one repo
python3 tools/fetch_trending.py --repos a/b,c/d           # several at once
python3 tools/fetch_trending.py --only-pinned             # just refresh the PINNED list
```

Add `--resummarize` to rewrite the summary of an existing repo (it re-fetches the README
and regenerates the summary):

```bash
python3 tools/fetch_trending.py --repos owner/repo --resummarize
```

It fetches metadata (and the README + a summary only if the repo is new), merges it into
the matching `data/<language>.json` (or `data/other.json` when the language is not covered),
then rebuilds `data/all.json` and `data/catalog.json`. A full run
(`python3 tools/fetch_trending.py`) is only needed when you want to pick up the current
trending boards — it refreshes every trending repo's metadata and is far heavier.

To keep a repo collected on every full run, also add it to the `PINNED` list at the top of
the script.

## Refreshing stars and other live fields

To bring every collected repo's `stars` / `forks` / `pushed_at` / `open_issues` / … up to
date without touching summaries, tags or the trending boards:

```bash
python3 tools/fetch_trending.py --refresh
```

It walks all of `data/`, refreshes the live fields, bumps `last_seen` / `seen_count`, re-sorts
by stars and rebuilds `all.json` + `catalog.json` (a full 3130-repo pass takes about a minute).
It goes through the GraphQL API in batches of 100 aliases (~1 rate-limit point per batch),
**not** one REST call per repo — the REST quota is 5000 requests/hour, so a per-repo loop
dies half way through and leaves the later files untouched. Repos that no longer resolve
(renamed, deleted, made private) are kept as they are and listed at the end.

A repo whose `language` changed is moved to the matching `data/<language>.json` (or
`data/other.json`), so one repo is never stored twice.

## Automatic updates (GitHub Actions)

Two workflows live in `.github/workflows/`:

- `update-trending.yml` — on the 1st of each month (22:10 UTC, 06:10 Beijing the next day) it runs on the pinned
  toolchain (`gh` 2.102.0 from the cli/cli release tarball, checked by sha256, and pi
  `1.1.0` from npm) and counts on two repository secrets: `DEEPSEEK_API_KEY` (pi's model
  plus the script's Chinese summaries) and `GH_TOKEN` (a PAT used by `gh` for metadata /
  READMEs and for `git push`; without it the run falls back to the built-in `GITHUB_TOKEN`).
- `deploy-pages.yml` — deploys the static site. A push made with the built-in token does
  **not** trigger it, so the update workflow dispatches it explicitly when no PAT is set.

The update workflow is driven by **pi**: it runs `tools/fetch_trending.py`, checks
`tools/check.py`, rewrites summaries that came out wrong with `--resummarize`, commits the
new repos and stops. The workflow only installs the tools, pushes (with a fallback commit
if pi left changes behind) and writes a per-run summary of the added repos. The step-by-step
briefing for that run is `.github/prompts/update-trending.md`; when changing the data rules
here, keep that prompt in sync. Run it by hand with `gh workflow run update-trending.yml`
(`-f languages=… -f since=… -f limit=…`), or add specific repos only with
`-f repos=owner/repo,owner/repo`.

## Layout rules

- Newspaper theme: paper background (`--paper`), double rules (`3px double var(--rule)`),
  dark-red accents (`--accent`), monospace body text. New components reuse the variables in
  `:root`; do not start a second palette.
- **No italics anywhere**: `em/i/cite` are reset to upright; separate levels with weight,
  color, a dark-red left rule, or `letter-spacing`.
- Fixed language colors: JS `#c9a227`, TS `#2f6fb0`, Python `#3572a5`, Java `#b07219`,
  Go `#0091b3`, Rust `#b5651d`, C `#5b5b5b`, C++ `#f34b7d`, all `#8c1d18` — each has a copy
  in `LANG_COLOR` in `index.html` and as `--lang-*` in `trending.css`.
- Cards: the title is `owner/repo` (links to GitHub), the body is `summary`, and the footer
  is `★ Star`, `更新于 YYYY.MM.DD` (the repo's last push) and `收录于 YYYY.MM.DD`
  (`added_at`, day precision) at the right edge. The footer sticks to the bottom with
  `margin-top:auto`; do not add "today +N". `added_at` is shown only in that footer slot
  and used as the default sort key (收录时间).
- The reading area `.reader-scroll` is one scroll container; the left list `.timeline` is
  another. Scroll a card into view with `scrollIntoView`, and highlight with `aria-current`.
- The search box (`.board-tools .search`) filters by `full_name` (owner + repo,
  case-insensitive) and filters both the left list and the cards at once.
- The domain bar (`.domain-bar` / `.dchip`) is a single-select filter over `domains`; the
  selected chip also filters the left list and the cards, and the result count switches to
  "筛出 N / total". Cards show `primary_tag` and `primary_domain` as small chips in the footer.
- Responsive breakpoints: at `1080px` the cards collapse to one column, at `900px` the left
  column becomes a drawer, at `640px` the reader bar wraps to two rows.
- On narrow screens use `grid-template-columns:minmax(0,1fr)`, not `1fr` (the auto minimum
  gets stretched by the content's min size).

## How to verify changes

```bash
python3 -m http.server 8137 &
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --hide-scrollbars --user-data-dir=/tmp/cp \
  --window-size=1500,1000 --screenshot=/tmp/shot.png --virtual-time-budget=9000 \
  "http://localhost:8137/index.html"
```

Note that headless Chrome has a minimum window width of about 500px, so `--window-size=390`
just crops a 500px layout into a 390px image — it does not mean the narrow layout actually
overflows; check the measured width instead. Use a temporary `--user-data-dir` to avoid
hitting a stale cache.

## Things not to do

- Do not add a backend, database, or front-end framework; keep it "static JSON + one HTML +
  one CSS".
- Do not add a build step, and do not merge the JSON into a bundle.
- Do not inline a full set of styles in the page, or copy the CSS.
- Do not introduce CDN / remote fonts / installed-font dependencies; fonts come only from
  `assets/fonts/fonts.css`.
- Do not generate summaries that are not grounded in the README.
